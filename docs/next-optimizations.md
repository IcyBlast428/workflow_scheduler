# 下一轮优化建议

日期：2026-09-30。基于当前代码检查，以下是建议，尚未实施。可视化流程编辑按用户要求暂缓；在线只读文件查看已完成。

## 优先处理

### 1. 执行文件巡检改为增量处理

`app/bootstrap/operations.py` 的 maintenance 每 60 秒遍历全部运行 JSON，list_runs 也遍历目录并检查文件。当前文件至少保留 90 天，生产每月约 200 万次执行；若这些执行全部来自本版本，文件数量会达到百万量级。这是根据实现和用户数据量推算的风险，本地 200 万条合成 SQL 日志没有产生同等数量的文件，因此此前测试未覆盖它。

建议把活动执行、待补写记录与完成记录按目录或索引组织；周期巡检只处理未完成和待补写集合。完成文件按日期分桶，过期清理由游标分批推进，设置每轮文件数/时间预算。不要通过缩短业务要求的日志保留期解决遍历开销。

验收：百万文件下，任务详情读取、后台维护耗时和启动恢复耗时均有明确上限；数据库断开后的记录仍能补写。

### 2. 日志归档成为可观测的维护能力

当前有安全的分批归档脚本，旧记录移入同库归档表，归档表没有自动期限，系统调度历史也会继续增长。

建议页面提供在线/归档容量、最早记录日期、最近归档时间、待处理进度和失败原因；配置维护窗口、批量预算和暂停开关，增加单实例维护锁。在线继续至少保留 90 天。归档的长期保留、备份和最终清理期限由业务确定，最终清理单独受控。

月分区作为后续方案，在真实 GaussDB 类型/版本上验证索引、主键、归档与回退后实施，不直接套用 PostgreSQL 的语法。

### 3. 总览统计独立于明细日志

当前累计失败统计仍每 60 秒按在线日志分组计数；最近失败排行按最近 24 小时最多 1000 条计算，页面已注明这个范围。高频任务场景下，1000 条无法覆盖完整一天，排行可能遗漏较早失败。

建议维护按任务/小时的成功、失败、取消、超时、跳过和耗时汇总；累计值增量更新，历史回填分批执行并保证可重跑。页面展示统计覆盖时间和刷新时间，详细日志只负责定位单次执行。

## 随后处理

### 4. 通知可靠性与告警管理

`execution.py` 目前使用内存通知队列，重启不能恢复待发送通知；短信已有连续失败抑制，邮件仍会随失败不断发送。

建议用持久化待发送记录，与执行结果事务关联；记录网关接受/拒绝/结果未知，提供页面查询和人工处理。补充邮件告警冷却、异常恢复通知与接收组测试。重试仅在网关幂等或确认未发送时执行，不能把请求超时直接当作未送达。

设计依据：AWS 的 transactional outbox 文档讨论事务状态与消息发送的一致性，也指出重复消息需要幂等处理：https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html 。这一模式可以直接应用在现有平台数据库中，不要求采用 AWS 服务。

### 5. 显示调度延迟与未执行原因

已有全局/任务并发限制与 APScheduler 错过调度事件。建议补充预计触发时间、实际开始时间、延迟、占用名额、超期/跳过原因，并按任务显示“上次应运行但未完成”的状态。

任务分别选择超期丢弃、合并一次或人工补跑；补跑需要业务幂等约束。持续长任务与短检查任务可评估分组并发配额，避免长任务挤满全部名额。保持调度器单实例。

APScheduler 官方说明线程池容量、misfire 与 coalescing 会影响迟到任务的执行方式：https://apscheduler.readthedocs.io/en/3.x/userguide.html#missed-job-executions-and-coalescing 。

### 6. 让运行记录关联代码版本

只读浏览器显示当前部署文件。建议每次执行记录发布版本/提交号、入口文件校验值和依赖环境版本；代码发布保留不可变版本目录，运行记录引用版本，无需每次执行重复复制全部源码。这样能追溯“当时到底运行了什么”。

### 7. 提升上百任务的日常操作效率

增加任务收藏、标签、保存筛选条件、“我负责的任务”、可复用日志筛选；增加受控的批量暂停/启动，执行前显示影响列表和运行中任务处理方式。负责人和说明已经存在，优先在这些信息上做筛选。

### 8. 真实环境验收与故障演练

目前本地 PostgreSQL 验证了 SQL、ODBC、事务和 200 万条短合成日志查询，尚未证明真实 GaussDB 和完整运行链路的吞吐。

下一轮测试覆盖：100 个分钟任务、长短混合执行、持续写入与分页查询、较大日志、真实文件数量、通知网关异常、数据库短暂不可用和服务重启。收集启动/排队延迟、页面响应 P95、查询耗时、连接数、维护积压、磁盘增长和漏执行情况；补充实际备份恢复演练。

## 建议顺序

先处理执行文件巡检、归档维护和统计汇总，再处理通知与调度诊断，随后完善版本追溯和操作效率。每一项独立验收，避免一次发布过多变更导致无法判断收益。
