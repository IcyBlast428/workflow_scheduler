# Workflow Scheduler 项目审阅

2026-11-18，基于 `main` 的 `b6598a8` 和现场工作区，包括尚未提交的安装和 Nginx 配置。项目有 600 个 Git 跟踪文件。审阅沿调度、执行、数据库、发布、管理界面和部署入口展开。最先要修的是发布与派发的死锁，以及普通维护可能误停活动任务的问题。

## 一、优先修复的运行故障

| 编号 | 触发条件及影响 | 改进和验收 |
| --- | --- | --- |
| 1 · 发布和派发可能死锁 | 发布或回滚先拿配置锁，再拿准入锁。队列派发在准入锁内调用需要配置锁的提交函数。两条线程各拿到第一把锁时可以永久互等，后续需要任一把锁的操作也会排队。用真实入口和记录锁顺序的替身确认了两个方向。[发布](../app/bootstrap/task_packages.py#L584) · [准入](../app/bootstrap/admission.py#L195) · [提交](../app/bootstrap/core.py#L212) | 统一锁顺序，把耗时的文件校验移出双锁区，并在切换前复核版本。用并发发布与派发覆盖两个入口，验收两者均能结束，且同一请求只产生一条执行。 |
| 2 · 普通维护可能误停活动任务 | 心跳先写本地恢复文件，数据库短暂写入失败时文件会保留。每分钟的普通维护补写成功后，也会把其中的运行中记录交给「重启遗留任务」处理，进而停止对应进程或 systemd 单元并登记为中断。隔离调用确认进入该分支，终止操作已拦截。[普通维护](../app/bootstrap/operations.py#L266) · [进程处置](../app/bootstrap/operations.py#L236) · [恢复重放](../app/bootstrap/journal.py#L143) | 普通维护只补写状态。启动恢复独立核验执行归属。以执行编号串行化重放与状态更新。用例应覆盖数据库闪断后原任务继续运行、旧心跳与刚完成的终态同时到达。 |
| 3 · 今日执行矩阵可能耗尽自己的数据库连接池 | 缓存重建时已持有一个连接，又逐条调用 `read_run` 借连接。配置允许调度器连接数为 1、溢出为 0。存在活动记录且没有本地恢复文件时，用真实连接池配内存数据复现了调度端接口 HTTP 500。默认池容量较大时，活动记录仍会增加查询。[矩阵读取](../app/bootstrap/execution_matrix.py#L80) · [连接池配置](../app/bootstrap/platform_config.py#L21) | 先批量取所需活动数据并释放外层连接，再叠加本地恢复记录。用单连接池、大量活动执行、无活动执行三种条件验收。 |

## 二、反复消耗数据库或文件系统的路径

| 编号 | 已核实的开销 | 建议 |
| --- | --- | --- |
| 4 · 执行记录列表逐条重查 | 两次批量查询并合并后，又为每个执行编号单独查 journal。两批记录一致、没有本地恢复文件时，隔离计数为 50 条记录 52 次业务查询，100 条 102 次。尚未计入借连接时的健康检查。任务详情也使用这个函数。[列表循环](../app/bootstrap/operations.py#L128) · [单条查询](../app/bootstrap/journal.py#L91) | 复用两批结果，对缺项做有界批量补查。本地恢复文件覆盖旧数据库行。给列表测试增加查询次数断言，并覆盖数据库断线回退。 |
| 5 · 总览为闲置的累计失败数拿独占锁 | 总览判断失败任务只用 `last_status`，共同的统计函数却会加载所有任务的累计失败数。缓存过期后，这条路径对两张统计表加独占锁。若有历史数据待补算，还会在锁内聚合。完成记账也使用这些表；读取失败时，已查到的任务状态还会一起丢失。目标 DWS 的等待时长待测。[总览](../app/api/task/views.py#L354) · [统计锁](../app/bootstrap/failure_totals.py#L14) · [完成记账](../app/bootstrap/run_summary.py#L20) | 总览只读需要的任务状态。对确实展示累计值的列表，正常读取走只读路径，归档或统计不一致时才重建并加锁。 |
| 6 · 心跳走完整恢复写入流程 | 每个持续执行的任务约每 5 秒更新一次心跳，仍需读取整条记录，写临时文件并同步磁盘，再锁 journal 表、删除并重插整行。20 个长任务按周期估算，每分钟约 240 轮，实际频率受写入耗时影响。[心跳](../app/bootstrap/execution.py#L234) · [持久化](../app/bootstrap/journal.py#L106) · [替换行](../app/bootstrap/auxiliary_store.py#L172) | 先修复第 2 项，再单独更新或合并心跳。保留接收、启动和终态的持久化保障。在目标环境比较每分钟事务数、磁盘同步次数及结束记账延迟。 |
| 7 · 发布清单已有的数据被反复扫描 | 调度器约每 2 秒发布快照，任务发现缓存约 3 秒。轻载时约每 4 秒触发一次全量发现。每个已发布版本先枚举候选入口和校验路径，随后又用发布清单覆盖这些值并再校验一次。[快照循环](../app/bootstrap/runtime_snapshot.py#L68) · [发现缓存](../app/bootstrap/task_loader.py#L232) · [清单覆盖](../app/bootstrap/task_packages.py#L722) | 直接从不可变版本清单构建任务描述，保留实际选定入口的有效性检查。快照只更新运行中的可变字段，在发布、回滚或配置变更时刷新描述。 |
| 8 · 已回收任务每分钟触发一次无效对账 | 有已保存计划的任务进入回收站时会增加配置版本，但成功移除调度后没有记录该版本已应用。普通维护发现版本不符，逐项强制刷新，任务发现又会排除回收站，所以同一任务可持续触发全量发现和异常日志。[回收](../app/bootstrap/task_packages.py#L668) · [配置版本](../app/bootstrap/schedule_config.py#L425) · [对账](../app/bootstrap/operations.py#L317) | 在撤销调度成功后记录对应版本的应用结果，或让对账明确识别回收态。覆盖回收、维护两轮、恢复后三个状态。 |
| 9 · GitLab 空闲检查读取整个差异快照 | 开启 GitLab 后，后台约每 5 秒检查一次。默认正式扫描间隔为 300 秒，但每次判断是否到期前，已经在持锁事务里读取并解析含文件差异、比对缓存和任务清单的完整 JSON。前端请求简要状态也会读取完整快照。[定时判断](../app/bootstrap/gitlab_updates.py#L405) · [状态摘要](../app/bootstrap/gitlab_updates.py#L359) · [后台循环](../app/bootstrap/gitlab_updates.py#L425) | 把上次扫描时间、版本、租约和简要计数独立保存。到期执行扫描或查看具体差异时再加载正文。保留连接变更和 webhook 的及时触发。 |

## 三、用户能直接遇到的错误与规模上限

| 编号 | 触发条件及证据 | 改进方向 |
| --- | --- | --- |
| 10 · 无关文件可阻断 GitLab 任务发布 | 目录发现先递归枚举整个项目，之后才过滤任务根路径。模拟仓库只有一个任务，其余均为无关文件。9,999 项时发出 100 次目录请求并成功；恰好 10,000 项，即使最后一页明确没有下一页，也被判为不完整。该状态会阻止基于目录清单的发布和删除，依赖重建发布也走这段校验。[目录分页](../app/bootstrap/gitlab_tasks.py#L42) · [发布限制](../app/bootstrap/gitlab_updates.py#L346) · [重建校验](../app/bootstrap/gitlab_tasks.py#L339) | 以配置的任务根及显式绑定目录为范围分页，处理根重叠、末页恰好满页、目录缺失与权限错误。只有受管范围完整时才允许判定任务已删除。 |
| 11 · 版本清理会在积累后失效 | 先取最新 10,001 条版本记录，再在内存跳过已经清理的条目。累计超过 10,000 条就标记扫描不完整，在线和离线清理共同拒绝执行。用 10,000 条已清理审计记录加 1 条旧版本复现。另一个限制是预览列出所有候选，超过 100 项时执行直接拒绝。[版本扫描](../app/bootstrap/version_storage.py#L15) · [执行门槛](../app/bootstrap/version_cleanup.py#L44) · [离线入口](../scripts/cleanup_versions.py#L40) | 分页完成引用检查，保留审计行并排除已清理项，用确定顺序每次生成最多 100 项的可执行计划。每批仍复核引用、保留数和确认指纹。 |
| 12 · 失败摘要遗漏真正的日志末尾 | 保存历史时只读取文件开头 63 KiB，再对这段数据取尾部。用 102,426 字节的日志验证，记录中的退出原因成功保存，但只存在于文件最后一行的具体报错没有进入数据库摘要。完整文件仍在时可下载查看。[文件读取](../app/bootstrap/operations.py#L175) · [摘要截取](../app/bootstrap/storage_policy.py#L94) | 失败时直接从文件末尾按预算读取，并准确处理 UTF-8 边界。分别验证成功日志开头、失败日志末尾、平台记录的原因和通知输入。 |
| 13 · 并发归档会让历史分页重复 | 选择「全部」时，在线与归档记录分两条 SQL 查询。归档在两次读取之间提交，同一条记录可能出现两次并挤掉另一条。用两份顺序快照调用真实分页函数，容量为 2 的页返回了两个相同 ID。[分页查询](../app/bootstrap/history.py#L53) · [归档事务](../app/bootstrap/history.py#L75) | 两来源用单条 `UNION ALL` 统一排序、游标和限量，或者在一致的读快照中获取。覆盖边界时间相同且后台正在归档的情况。 |
| 14 · 总览会合并两次独立执行 | 历史查询只携带任务 ID，后端和浏览器又按任务及接近的起止时间去重。隔离样例中，同任务两次独立执行分别占第 0–3 秒和第 1–4 秒，页面仅留下覆盖第 0–4 秒的一条。[历史标记](../app/api/task/views.py#L276) · [前端合并](../frontend/src/cpuTimelineData.js#L191) | 携带并使用执行 ID。只有缺少 ID 的旧数据才做受限的跨来源匹配。验证同一执行的实时和历史记录能合并，不同并发执行各自显示。 |
| 15 · 切换设置分栏会丢草稿 | 进入分栏时重新请求策略并以返回值覆盖表单，同时把新值标为已保存。在实际 Vue 组件配模拟接口的验证中，修改的发布分支和从 2 改到 7 的配额，在切走后返回时都恢复为旧值。[分栏切换](../frontend/src/components/AdminPanel.vue#L66) · [加载与覆盖](../frontend/src/components/OperationalWorkbench.vue#L60) | 各分栏独立保存草稿和修改状态。首次进入加载，主动刷新时处理已有修改。补测切栏、离开设置页以及较慢请求晚到。 |
| 16 · 混用两版前端文件仍可能通过安装检查 | 当前工作区新增的安装检查确认入口 HTML 存在，并校验构建清单中的文件，但没有读取 HTML 里的实际 JS、CSS 地址。隔离验证记录到入口正文读取次数为零。若 HTML 来自旧版，清单和资源来自新版，安装检查可以通过，浏览器却会请求已不存在的入口。[安装校验](../scripts/deploy.py#L229) · [打包校验](../scripts/package_release.py#L76) · [实际入口](../app/dist/index.html#L36) | 打包和安装共用一套本地入口资源校验，同时检查 HTML、清单和文件三者的一致性。新增一组「旧 HTML 加新资源」回归样例。 |

## 处理顺序和验证范围

1. 先修第 1–3 项，增加并发、数据库短暂不可用及最小连接池的回归。三项都可以先在隔离环境稳定验证。
2. 第二批处理第 4、5、8、9 项，减少每次请求及空闲状态下的固定工作。比较每请求查询数、空闲每分钟 SQL 数、完成记账的第 95 百分位延迟。第 6 项会改变心跳写入路径，需要额外做进程退出和恢复测试。
3. 第 10–16 项按现场功能使用情况安排。其中第 16 项涉及当前未提交的安装检查，适合随该改动补上回归。驱动去重排在调度和查询修复之后。

本次在 Windows 运行了 37 项部署、发布包、依赖分析及服务监督相关 Python 测试，25 项通过，12 项因平台条件跳过。前端配置中的 20 组 Node 测试脚本全部通过。数据库计数、并发路径、日志样例、组件交互和 GitLab 目录边界采用隔离验证。审阅时本机 Docker 引擎不可用，完整 PostgreSQL 集成回归未执行；以上数字不包含生产 DWS 压测、真实 GitLab 或浏览器端到端验证。
