# 部署与平台数据库建议

基于当前项目代码与官方资料，2026-10-22。这里只记录选型建议，本次没有迁移生产数据或更换生产部署。

## 建议结论

- 长期建议使用容器交付 Web 和独立 Scheduler，固定 Python、系统库和数据库驱动，方便复现、升级和回滚。只有一台固定内网服务器、已有成熟 systemd 运维时，可以继续当前方式，先解决数据拆分与备份，不必为容器本身重建运维。
- 生产平台数据优先独立放在 MySQL / PolarDB for MySQL；当前页面配置、建表和平台适配已支持这条路径。小规格独立托管 MySQL 也可以，不必为了平台元数据直接购买大型集群。
- GaussDB 事务型数据库可作为候选，但必须确认具体型号、版本、驱动和 SQL 兼容性。GaussDB(DWS) 是另一种数据仓库场景，不因名称相同就视作等价选择。当前页面将业务连接展示为“PostgreSQL / GaussDB”，内部仍为 `postgresql+psycopg`，不是已经完成全部 GaussDB 产品适配。
- SQLite 保留给本地验证、小规模单机部署与低写入频率的辅助配置。ClickHouse 适合后续历史分析，不建议承担本平台的唯一主库。

## 为什么倾向容器交付

本项目同时涉及 Python 子进程、每任务独立虚拟环境、离线 wheels、数据库驱动及系统库。将这些版本固定到镜像，比依赖服务器上逐步安装的软件更容易复现问题；Web 与 Scheduler 的升级和资源分配也更明确。

建议拓扑为：反向代理 → Web；Web 通过内部控制接口访问一个 Scheduler；Scheduler 启动任务子进程；平台和业务分别使用独立数据库连接。当前 APScheduler 3.x 不应通过增加 Scheduler 副本来扩容，见 [官方多进程说明](https://apscheduler.readthedocs.io/en/3.x/faq.html#how-do-i-share-a-single-job-store-among-one-or-more-worker-processes)。本项目已有对应的两个 systemd 服务，但尚未提供经过验收的 Dockerfile / Compose 部署。

容器化需要同时落实以下事项：

1. Web 与 Scheduler 共享同一份 `WFS_DATA_DIR`，任务发布目录及虚拟环境在服务内使用一致的绝对路径；生产密钥通过部署配置注入。配置连接仍保存在该目录内的加密 SQLite 文件，独立平台库不代替这份配置存储。
2. 数据、任务版本、任务输出和日志使用持久卷，并做备份恢复演练；容器重建不能丢失这些文件。[Docker 卷文档](https://docs.docker.com/engine/storage/volumes/)说明卷的生命周期独立于容器。
3. 固定系统、CPU 架构和 Python 版本。构建匹配的离线 wheels；GaussDB 所需客户端库、CA 与 ODBC 配置也要部署到镜像或指定挂载路径。
4. 配置 CPU、内存、子进程数量与停止宽限时间，验证任务超时、取消、服务重启与子进程回收；Scheduler 控制端口仅对内部服务开放。
5. 容器内当前仍是多个任务子进程共用服务权限。任务虚拟环境隔离依赖，不是安全沙箱。若需要不可信任务隔离，应另行设计每次执行独立容器/工作节点，不能直接把当前 Scheduler 多复制几个。

## 平台数据库如何选

平台主库承担任务配置、用户会话、调度状态、执行结果、计数和审计，主要是小范围读取和事务更新。业务库承担任务访问的订单、报表或其他业务表。两者的数据库引擎可以不同。

| 候选 | 适合本项目的用途 | 取舍 |
| --- | --- | --- |
| SQLite | 开发、本地验证、小规模单机 | 无额外服务；WAL 允许读写并行，但同一文件同时仍只有一个写者，不适合跨主机共享网络文件使用 |
| MySQL / PolarDB for MySQL | 首选生产平台主库 | 当前管理页面支持；可沿用团队现有运维、备份和监控，需要容量、连接数与慢查询治理 |
| PostgreSQL / 事务型 GaussDB | 团队已有成熟支持时的候选平台主库 | 适合事务型访问；旧平台入口与页面 MySQL 配置不是同一条路径，需要目标版本迁移、驱动、并发和故障恢复验收 |
| ClickHouse | 大量历史执行记录的汇总、趋势分析 | 官方定位为列式 OLAP；本项目平台适配尚不支持它，不应直接替换账号、状态与事务主库 |

SQLite 的限制见 [WAL 官方说明](https://www.sqlite.org/wal.html)；这不是“任务数量一多必然变慢”，真正需要观察的是同时写入、每秒完成事件、单次事务耗时、日志体积和查询方式。ClickHouse 的选型定位见 [官方介绍](https://clickhouse.com/docs/get-started/about/intro)。华为的 [GaussDB 开发指南](https://support.huaweicloud.com/intl/en-us/distributed-devg-v8-gaussdb/gaussdb-12-1817.html)还涉及配套 libpq / OpenSSL；不能仅凭 PostgreSQL 名称判断驱动可用。

## 拆分和日志增长的实施顺序

1. 先建立独立平台数据库和最小权限账号。业务任务的 `NewDB('连接标识')` 指向业务库；平台固定标识 `platform` 仅供服务内部使用。
2. 同一 PolarDB 集群中新建一个数据库，只完成逻辑和权限分离，仍共享计算、IO、连接容量与故障影响范围。需要互不干扰时应进一步使用独立实例/集群，并按真实负载决定规格。
3. 平台状态查询要求及时看到刚写入的状态。PolarDB 可先使用主地址，若选择读写分离集群地址，要验收跨连接的读后写一致性，不能只确认单会话一致性。见 [PolarDB 地址与一致性说明](https://www.alibabacloud.com/help/en/polardb/polardb-for-mysql/user-guide/connection-connection-endpoints)。
4. 迁移前备份原库、任务文件、连接配置和密钥；停止调度并等待任务结束，迁移核对行数、索引与时间字段，再统一重启 Web/Scheduler。页面保存新连接不会搬迁历史数据。
5. 优先控制日志增长：保留近期明细和按任务/日期的索引、限制列表范围、分批归档；累计汇总用于总览。当前历史表仍含 `tasklog` 长文本，单纯换引擎不能解决无限增长。下一阶段可将长输出迁到文件/对象存储，主库只保留摘要、状态和输出位置，并设计保留期限。
6. 确实有海量长期分析需求时，再异步同步执行明细到 ClickHouse，失败可补传，不能阻塞任务完成事务。这是后续方案，本次没有加入同步组件。

当前 MySQL 平台写事务用 `wfs_platform_lock` 单行锁保护旧逻辑的正确性，事务会排队。任务量增长时，要先测完成写入吞吐和锁等待，再评估改成针对任务/执行记录的行锁与原子更新；仅升级数据库规格不能消除这项串行化。

容量评估至少记录：每日执行次数、峰值并发与完成次数/秒、每次日志字节数、在线保留天数、归档增长量、数据库锁等待、查询 p95 和磁盘余量。上线数据库类型变更前，应以这些指标进行代表性压力测试与恢复演练，不给出未经测量的“最多支持多少任务”承诺。
