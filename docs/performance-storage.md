# 执行历史、日志摘要与热点查询优化

执行详情继续分段读取保留的日志文件，单段最多 64 KiB，完整文件仍可下载。历史列表不加载日志正文。新完成的执行在数据库中只保存可配置的摘要：成功默认 2 KiB，其他结果默认 16 KiB。成功摘要保留开头，失败摘要保留执行原因和末尾，截断处会提示。摘要按 UTF-8 字节截断，不会切断汉字；提示文字不计入片段额度。

此设置不会修改已经保存的历史日志，也不会缩短告警原有的日志输入。告警仍使用原来的最多约 63 KiB 内容；日志文件继续遵循独立的容量和保留期限。文件过期后只能查看数据库摘要，设置保留期限时应结合排障和审计需求。

## 管理界面

系统管理的存储页面提供历史存储策略，保存时校验版本，防止两个管理员覆盖彼此的修改：

| 选项 | 默认值 | 范围与含义 |
| --- | --- | --- |
| 自动归档 | 关闭 | 开启后由单实例调度器每轮维护执行 |
| 在线保留天数 | 90 天 | 90～3650 天，只移动早于截止时间的记录 |
| 单批条数 | 200 | 1～1000，一批复制、逐行比较内容后，在同一事务移除在线副本 |
| 每轮最多批数 | 10 | 1～50，达到限额后留待下一轮 |
| 每轮时间预算 | 5 秒 | 1～30 秒，在批次边界检查；正在执行的事务会先完成或回滚，单批可能超出预算 |
| 成功日志片段 | 2 KiB | 0～16 KiB，0 表示只保留摘要提示 |
| 非成功日志片段 | 16 KiB | 1～63 KiB，保留执行原因和末尾 |

页面显示上轮归档时间、条数、批数、耗时、是否还有剩余、是否达到时间预算和错误信息。默认每轮最多 2000 条；实际吞吐受查询耗时和时间预算限制，应观察剩余积压，而不能把这个上限当成吞吐保证。后台每轮维护后等待约 60 秒；维护本身的耗时会增加两轮之间的间隔。

**归档仍位于同一数据库。** `wfs_run_history_archive` 保留全部原始字段，历史页面选择“归档”或“全部”即可查询。归档减少在线表体积，不会释放数据库总占用空间，也不会删除审计历史。需要长期冷存储或永久清理时，应另行制定保留策略及备份验证流程。

归档遇到副本不一致、写入失败或校验失败时，当前批次整体回滚，在线原记录保留；已经提交的批次保持可查询。自动归档默认关闭，升级代码不会自动移动旧历史数据。

## 现有数据库的索引升级

新建数据库已包含两个索引：

- `idx_wfs_run_start_id`：全局开始时间轨迹的范围查询和排序。
- `idx_wfs_executions_created_id`：全局执行列表及过期执行索引清理。

已有数据库先使用与服务一致的环境变量、运行账号和 Python 环境预览：

```bash
cd /data/workflow_scheduler
.venv/bin/python scripts/upgrade_performance_indexes.py
```

确认需要建立的索引后，在维护窗口执行：

```bash
.venv/bin/python scripts/upgrade_performance_indexes.py --apply
```

该脚本不会读取或改写执行内容，只创建缺失的索引；事务锁用于避免并发重复升级：本地 PostgreSQL 验收使用事务咨询锁，GaussDB/DWS 使用 `wfs_schema_version` 表的排他锁，执行完成后再次运行不会重复创建。大表建索引可能阻塞写入，运行前应评估维护窗口和可用磁盘。此脚本不使用 `CONCURRENTLY`，以避免把 PostgreSQL 专用部署假设套到目标 GaussDB/DWS 版本。上线仍需在实际数据库版本确认执行计划和建索引耗时。

## 查询缓存与手动归档

概览的历史开始标记共用 5 秒缓存，新的实时标记仍在每次响应中合并；同进程完成写入会立即使缓存失效，其他 Web 进程最长等待缓存自然过期。这样多个浏览器不会每次都重复查询相同历史，实时执行标记也不会被缓存冻结。

`scripts/archive_history.py` 仍可预览和有界归档。归档现在按批次复制与校验，避免对每条记录反复往返查询；每批仍保留完整事务校验。手动归档和自动归档都至少保留 90 天在线历史，都不会永久删除历史记录。

归档仅搬移已经完成小时统计汇总的记录（`summary_version=1`）。未汇总旧记录继续保留在线，由原有后台补算处理；存在这类旧记录时，归档状态仍可显示有积压，不会把统计覆盖误报为完整。
