# 剩余改进与操作手册

日期：2026-10-29。承接[前五项操作优化](operational-improvements.md)，本轮补齐现有任务管理、发布和运维能力。拖拽式流程编排器按用户要求继续暂缓。

## 能力与默认行为

| 能力 | 操作入口 / 行为 |
| --- | --- |
| 参数化执行、业务日期补跑 | 管理员任务详情 → 运行策略；补跑只允许管理员明确声明可安全重复执行的任务 |
| 自动重试 | 默认关闭；显式声明可重复执行并设定次数后启用，最多 3 次 |
| 候选代码试运行 | 代码版本 → 使用测试连接试运行；首次发布前也可执行，不替换正式版本 |
| 分组配额与完成提醒 | 账户与操作记录 → 发布与运维设置；任务运行策略设置期望完成时间、长运行阈值 |
| 维护员任务授权 | 管理员创建「任务维护员」，按任务编号或分组分配操作权限 |
| GitLab Webhook、分支过滤与发布门禁 | 发布与运维设置；独立启用 CI、指定作业、试运行、发布窗口 |
| 公共 SDK 与依赖追溯 | 新准备版本冻结 SDK；保留解析后的 wheels、版本和 SHA-256，支持离线重建 |
| systemd 执行隔离 | 每任务显式启用，先检测用户管理器/内核支持，再验证实际任务 |
| 连接生命周期 | 数据库连接 → 业务库；名称、负责人、用途、环境、引用、测试记录、停用/归档/删除 |
| 通知核对、问题处理 | 发布与运维设置 → 通知核对；总览 → 填写处理说明 |
| 版本清理与备份证据 | 账户与操作记录 → 版本占用、备份与恢复记录 |
| 界面体验 | 关键表单未保存提醒；沿用简化动效开关并减少背景绘制，窄屏布局与发布信息补齐 |
| 持续检查与环境验收 | GitHub CI、临时数据库故障回归、只读目标验收工具 |

上述开关不自动修改已有任务的业务行为，也不自动发布 GitLab 代码。生产数据库仍沿用现有 GaussDB/DWS 配置；应用仍由 Web 与单实例 Scheduler 的 systemd 服务管理。

## 1. 参数、重试与补跑

管理员在任务运行策略中保存默认参数，任务从环境读取：

```python
import json
import os
parameters = json.loads(os.environ.get('WFS_PARAMETERS_JSON', '{}'))
business_date = os.environ.get('WFS_BUSINESS_DATE', '')
source = os.environ.get('WFS_EXECUTION_SOURCE', 'scheduled')
```

参数必须是 JSON 对象，最多 50 个字段、16 KiB，字段名使用字母开头的字母/数字/下划线。参数和业务日期会进入执行记录，请勿放入密码或令牌。

自动重试只处理**明确以脚本失败结束**的正式执行；超时、取消、中断、跳过、试运行不自动重试。重试沿用原代码版本、参数和业务日期，次数最多 3 次，按配置等待时间指数退避。任务必须自行保证业务幂等，平台不承诺外部副作用恰好发生一次。

补跑通过管理员选择历史业务日期提交，使用提交时固定的当前发布版本。未来日期不接受；未声明可安全重复执行的任务不接受补跑。业务脚本必须实际使用业务日期，平台不会推断业务 SQL 或覆盖规则。

请求保存在 `admission.sqlite3`，维护模式期间不派发；容量不足时等待名额。已持久化但尚未派发的请求重启后继续等待；派发过程中失去确认的请求转为「待人工核对」，不自动重放。停用重试策略会阻止尚未派发的自动重试。请核对执行记录与外部业务结果，再决定是否重新提交。

分组配额计算已预留和运行中的名额，未配置分组沿用全局上限。自动计划遇到容量不足仍按现有策略记为跳过；配额不是公平调度队列。期望完成时间按 Asia/Shanghai 判断，用于总览提醒，不自动触发补跑或发送新通道通知。

## 2. 候选版本试运行

1. 在代码版本中获取 GitLab 候选代码，先完成依赖与语法检查。
2. 展开「试运行设置与执行请求」，将原连接标识映射到专用测试连接，例如 `orders=orders_test`。
3. 提交试运行，刷新请求并查看执行结果；需要时刷新发布检查。
4. 确认业务结果后再发布。启用试运行门禁时，必须存在同一候选版本的成功试运行记录。

试运行采用候选版本入口与解释器，最长 10 分钟，不调整正式调度和当前发布版本。任务数据及输出存放在 `trial-data/<任务编号>`，执行记录标记 `trial`，不计入正式历史统计、任务运行时间线或正式失败通知。

试运行只向 SDK 提供映射的测试连接；空映射不提供业务连接，也不回退旧 INI。映射不会识别脚本写死的地址、外部 API 或自建连接；普通进程仍是可信代码执行。**独立输出目录与测试连接不等于完整隔离的测试环境**，必须先审查业务副作用。

## 3. 任务维护员

先创建角色为「任务维护员」的账号，再在「任务维护员授权」读取该账户，填写任务编号或任务分组，选择所需能力：手动执行、修改调度及启停、审查与发布代码、查看源码。授权默认空，下一次请求生效；分组授权包含该分组后续新增任务。

维护员不能管理账户、通用业务连接、GitLab 凭据、平台发布策略或任务运行安全策略。试运行、幂等声明及自动重试仍由管理员管理。旧 viewer/operator 保持只读。`WFS_TASK_PUBLISHERS` 非空时继续作为发布用户名的额外限制，授权维护员发布时也须纳入该名单。

现有工作区的只读任务/日志可见范围继续共享；这套授权控制操作和源码访问，不提供按租户隔离日志的能力。任务执行权限不代表允许上传未经审核的不可信脚本。

## 4. SDK 固定与依赖重建

新版本准备时复制任务可用的 `app/common`、`app/bootstrap` 和根 Python 模块到版本内的 `shared-sdk`，排除业务配置、任务目录和页面，记录摘要。执行与发布校验该快照，不再随下一次平台代码更新自动改变公共模块。既有历史版本没有快照时仍按旧兼容方式执行，不能倒推其历史 SDK。

也可将 SDK 构建为私有 PyPI 包，先在独立目录检查产物，再由现有制品发布流程上传：

```bash
python scripts/build_task_sdk.py --version 1.0.0 --output /tmp/wfs-sdk-review
```

任务显式依赖 `workflow-scheduler-task-sdk==1.0.0` 时使用该独立环境中的 SDK；普通任务默认使用版本内快照，仍须在任务依赖中声明实际使用的第三方库，快照不会自动安装这些依赖。SDK wheel 只用于任务环境，不能作为平台环境安装包。版本号一经上传不应覆盖。

任务准备先从已配置的私有仓库下载兼容 wheels，解析完整依赖，再按本地 wheel 摘要安装；保留 `dependency-bundle.json`、`dependencies.reproducible.txt`、`requirements.lock` 及该次独立 wheel 目录。不依赖源码包在线编译，不配置公网兜底源。离线模式要求完整固定依赖，私有库认证仍由原加密配置管理。

在原 Python **补丁版本**、操作系统和架构下，可从保留制品重建到全新目录：

```bash
python scripts/rebuild_task_environment.py   --release /data/wfs/shared/data/task-packages/TASK/releases/VERSION   --destination /data/wfs/rebuilt-envs/TASK-VERSION
```

工具先验证 wheels 摘要，再用 `--no-index --require-hashes` 安装并执行依赖一致性检查；目标必须不存在。它不覆盖原环境，也不自动切换调度器。重建成功后仍须做任务业务验收，跨 Python/系统版本应重新准备候选版本。

## 5. systemd 隔离与资源限制

普通进程模式保留兼容。可选择 systemd 用户单元，限制整组内存、进程/线程、CPU，建立私有 PID/用户/挂载空间，隐藏平台数据、用户主目录和配置，代码/SDK/解释器只读，只有该任务数据与输出目录可写。取消/超时按单元清理整个进程组。

要求 Linux 内核及 systemd 支持这些属性、cgroup 资源控制和用户管理器；本机在 systemd 259 上完成实际隔离探针。仅检测到 systemd 版本不能代表支持，请在目标主机以任务服务账户运行：

```bash
python scripts/probe_task_isolation.py
```

任务须使用带冻结 SDK 的新准备版本，并切换到「仅允许指定连接」。共享 SQLite 业务文件在此模式下拒绝开放；网络数据库的 CA 文件会只读映射。不能建立隔离时执行失败，不自动降级。网络仍可用，未实施按任务网络白名单，也不构成多租户或任意恶意代码的安全承诺。

生产系统级 Scheduler 需要连接同一服务账户的用户管理器；安装步骤见 [systemd 手册](systemd-deployment.md#可选任务隔离用户管理器)。部署脚本只生成审阅文件，不擅自安装广泛 sudo/polkit 授权。

## 6. GitLab 事件与发布门禁

在服务环境中配置独立随机 `WFS_GITLAB_WEBHOOK_TOKEN`（至少 32 字符），统一更新 Web/Scheduler，然后在 GitLab 项目 Webhook 中设置：

- URL：`https://平台域名/api/integrations/gitlab/webhook`
- Secret token：与服务配置相同，不是 GitLab API 访问令牌。
- 选择 Push、Tag Push、Merge Request、Pipeline 事件，并启用 TLS 校验。

入口只接受已配置项目和事件，按事件 UUID 持久去重，多次通知合并为一次后续扫描。没有配置独立令牌时拒绝事件；令牌不回传页面或任务。Webhook 只唤起只读扫描，周期检查继续兜底，不自动合并、发布或删除。

发布设置支持关注分支通配规则、CI 流水线与指定作业、成功试运行、发布时间窗口。CI 读取固定 SHA 与目标分支最新匹配流水线；未通过、缺少指定作业或读取失败都阻止发布。门禁默认关闭，分支默认 `*`；窗口留空不限，支持跨午夜，按 Asia/Shanghai 判断。

预览显示检查快照；实际发布重新检查，并在激活前核对策略版本与时间窗口。回滚同样遵守发布窗口和启用的门禁。环境标记只用于提示，不切换数据库或服务，生产/测试仍需独立配置与数据目录。

GitLab 出站 API 继续只使用 GET。平台代码仍由受控的固定版本 systemd 部署流程管理，任务发布不能替代平台升级。

## 7. 连接、通知与问题记录

业务连接可补充名称、负责人、用途和环境。页面显示声明引用、连接授权引用、测试映射及最近测试结果。引用来自明确声明，不能自动发现脚本中的动态标识或硬编码地址；删除前仍须核对业务代码。

停用/归档阻止下一次通过 SDK 获取连接，不强制关闭业务脚本已打开的连接。平台库不能停用或删除。删除要求先停用、无已声明引用、版本一致并输入连接标识确认；不会删除数据库本身或 SQLite 业务文件。

通知失败或结果未知时，先向网关/接收方核对，再记录「确认送达」「确认未送达」或「已人工处理」及依据。原发送状态、次数与人工处理结果保留，不自动重发。总览问题也可记录处理人和说明；处理说明不改变任务结果。

## 8. 版本清理、备份与恢复

版本占用先生成清理计划。默认至少保留最近 20 个版本，并保护当前、准备中、保留期内执行引用、待派发/待核对请求引用和迁移基线；回收站也遵守相同保护。清理只针对完整扫描且无保留依据的旧版本，保留版本审计元数据，不删除任务数据与输出。

在线检查有时间/条数预算，达到上限就拒绝执行清理。存在待补写或尚未恢复的执行记录时也拒绝清理。已超过执行保留期的归档历史无法自动证明源码仍可追溯，清理前须核对业务长期留存要求。必须先进入维护模式、等待活动实例结束，输入计划中的完整确认文字；执行前重新检查引用和指纹，单次最多 100 个版本，不做后台自动删除。

历史记录较多时，停服务后执行完整引用扫描。以下路径使用实际固定平台 Python；生成的预览文件必须尚不存在：

```bash
# 已在页面进入维护模式、活动实例清零，并完成数据库/文件备份
sudo systemctl stop wfs.service wfs-scheduler.service
sudo /data/wfs/current/.venv/bin/python scripts/cleanup_versions.py   --environment-file /etc/wfs/wfs.env --data /data/wfs/shared/data   --keep 20 --preview /tmp/wfs-cleanup-review.json
# 人工核对候选列表，使用该文件的 fingerprint 和 confirm 原文；不要跳过预览
sudo /data/wfs/current/.venv/bin/python scripts/cleanup_versions.py   --environment-file /etc/wfs/wfs.env --data /data/wfs/shared/data   --keep 20 --execute --fingerprint '预览指纹' --confirm '预览确认文字'
```

工具取得 Scheduler 单实例锁，流式检查全部执行引用，发现活动/未恢复执行、容量扫描不完整、指纹变化即拒绝。执行异常时检查 `.cleanup-quarantine`；不得直接清空。核对数据库中的 cleaned 元数据、原目录和备份后再由运维处理残留。完成后统一启动 Scheduler/Web，确认就绪，再由管理员结束维护。

备份工具将策略、授权、执行请求、事件去重、试运行输出与依赖制品纳入现有文件备份。成功生成归档后记录备份时间、位置、大小；恢复校验记录写入目标目录，不改源数据。记录代表工具成功生成/校验文件，**不代表 GaussDB/DWS 数据库导入或业务恢复已验收**。密钥、数据库一致备份和业务核对仍按原恢复流程执行。

## 9. 自动检查与目标环境验收

`.github/workflows/ci.yml` 包含 Python 3.12 后端、页面/浏览器和 PostgreSQL 18.1 独立测试库验收；这些检查需在 GitHub 运行后查看实际结果，不能将本地通过描述为云端已通过。

`scripts/fault_drill.sh` 使用临时数据库、临时任务测试维护、重复请求、执行中断、失败重试和门禁；不停止本机服务或触发生产任务。只读目标检查可输出新的报告文件：

```bash
python scripts/accept_target.py --url https://平台域名   --database --output /tmp/wfs-target-review.json
```

带 `--database` 时使用当前部署进程的数据库环境，检查 SELECT 与必要表；不写数据、不触发任务、不发送通知。真实 GitLab 认证/CA、GaussDB/DWS 写入事务及故障切换、真实邮件/短信、备份导入和业务核对，必须在专用目标环境继续验收。

## 升级注意

本轮复用平台 payload 与 `admission.sqlite3`，没有新增平台数据库迁移。Web 和 Scheduler 必须使用同一数据目录并统一更新。更新前维护排空并备份，更新后核对就绪。旧版不认识运行安全策略和新请求队列，不能以滚动回退方式混用；回退前停止派发并核对待处理请求。
