# 任务排队、错峰与负载保护

## 第一版的运行方式

定时触发先写入本机 `WFS_DATA_DIR/admission.sqlite3` 的持久队列，再由单个调度服务派发。自动计划、参数化执行、试运行、重试、补跑共用排队名额；普通“执行一次”仍立即申请并发名额，名额不足时明确拒绝。所有业务进程，包括普通手动执行，都在真正创建进程时遵守启动间隔。全局、单任务、任务分组的并发上限同时生效。已有进程不被负载保护中断。

系统管理 → 运行策略 → **任务排队与负载保护**：

| 配置 | 默认值 | 行为 |
| --- | --- | --- |
| 全局并发名额 | 4 | 1–20，且不超过环境变量 `WFS_MAX_ACTIVE_RUNS`；包含已保留启动名额的请求 |
| 启动间隔 | 1000 毫秒 | 同一调度服务相邻业务进程的最小启动间隔，100–60000 毫秒 |
| 等待队列上限 | 1000 | 包含等待和派发中的请求 |
| 单任务等待上限 | 10 | 防止短周期、长耗时任务无限积压 |
| 最长等待 | 600 秒 | 自动计划还取任务 `misfire_grace_seconds` 的较小值 |
| 主机负载保护 | 关闭 | 根据实际机器负载验收后可启用 |
| CPU / 内存阈值 | 85% / 90% | 连续 3 次有效采样偏高暂停启动；连续 3 次 CPU 低于阈值 10 个百分点且内存低于阈值 5 个百分点后恢复 |

负载约每秒采样，启用保护时采样不可用或超过 5 秒未更新也等待。CPU 是所在主机（WSL 中为 WSL 虚拟机）所有核心的平均占用，并非单任务配额。并发 4 是保守起点，不是对所有机器的性能承诺。新限制不会杀死已运行的任务；调低并发后先自然排空。

## 错峰与准点任务

任务详情 → 运行策略 → **允许错峰的最大延迟**。默认 0，不主动延迟。允许灵活执行的任务可以设 1–300 秒，系统按任务标识计算固定偏移；同一任务刷新、重启后偏移一致。原计划时间完整保留，执行记录会计入实际启动延迟。不再在启动时给 interval 任务隐式增加随机偏移。

错峰与排队共用从原计划时间起算的等待期限，错峰超过窗口会拒绝本次计划并提示调整。改变调度配置或停用任务后，旧的待派发计划取消；删除后也不会再启动。发布新版本不会替换队列里已选定的旧版本。冻结版本及参数随请求保存，并参与版本清理保护；旧式可变任务目录仍应先迁移为受管发布版本，不能把普通目录当作不可变代码快照。

没有主动错峰不等于保证实时准点：并发、启动间隔、维护及资源压力可能推迟实际执行。需严格准点且无法容忍等待的业务，应单独安排容量或调度实例，并设较短的允许迟到时间。

## 超时、恢复与可见性

- 自动计划超过允许启动期限变为“等待超时”；队列满变为“未接收”。独立的“执行队列”页面可查原因，首页“需要处理”显示近 24 小时异常及当前积压。无自动补跑；需要业务核对后另行提交。
- 等待请求按到期派发时间尝试，容量不足会退后 1 秒，让其他任务有机会运行。偏移结束后仍需要并发名额。没有保证跨分组的严格公平性或优先级抢占。
- 已写入且尚未派发的请求，服务重启后可在原期限内继续。派发中崩溃变为“待人工核对”，不会自动重放；已派发的执行沿用现有中断恢复处理。不是“业务副作用恰好执行一次”的承诺。
- 同一任务同一原计划时间使用固定请求编号去重。维护期间新自动计划记录为已取消；此前等待请求保留，但等待期限继续计算。
- 页面显示等待、已派发、超时、未接收、取消和待核对；已派发并不表示执行成功。真正启动前仍可能因维护、取消、超时而不执行，可查看对应执行记录。
- 终态队列记录保留 7 天，分批清理；待核对记录保留。执行历史仍遵守原有保留规则。执行队列按每页 25 条分页，支持按任务名称、ID 和请求状态筛选全部保留记录；积压数量统计为完整计数。
- 本队列只恢复已经持久化的触发，不自动生成服务停机期间的全部历史计划。APScheduler 原有触发合并规则仍适用。

部署继续使用单个 systemd 调度服务与独立 Web 服务，同一 `WFS_DATA_DIR`、本地可靠磁盘。备份须包含 admission.sqlite3。升级会自动为请求表增加期限字段；老的等待请求不追溯添加期限，管理员应核对或取消。分布式多调度实例不共享本机限速器，不在此版支持范围内。

CPU 保护只能减缓新增工作，不能给已经运行的脚本设置硬上限。重任务可使用已有的 systemd 隔离与单任务 CPU 配额；任务分组的总 CPU 配额尚未实现。

## 验证

`python -m unittest discover -s tests -p test_dispatch_queue.py -v` 包含 100 个同时到期计划的有界队列、重复通知去重、容量不足时让出派发机会、超时、维护、崩溃不重放、停用任务、发布后的版本固定、启动并发竞争和负载恢复阈值测试，并用 12 个真实子进程验证并发与启动间隔。

前端 `dispatch-queue.spec.js` 检查配置保存、重新加载、移动端留白与横向溢出。

执行队列支持取消待派发请求、打开任务详情和查看已派发的执行记录。取消请求不等于停用调度。系统管理分为运行策略、发布设置、账户权限、审计记录、存储备份五栏，切换分栏保留正在编辑的内容。
